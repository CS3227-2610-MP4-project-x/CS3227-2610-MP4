## Context

The change introduces nine capabilities described in the delta specs. The repository has OpenSpec configuration, agent guidance (`AGENTS.md`), and UI guidance (`specs/ui-spec.md`), but no application code yet. `AGENTS.md` sets the stack: Next.js App Router with TypeScript, Route Handlers under `/api/v1`, PostgreSQL on Supabase behind a server-only repository layer, the SoC LLM behind a replaceable adapter, and Vercel hosting.

## Goals / Non-Goals

**Goals:**
- Give each role one clear AI feature: the Acceptance Criteria Check for developers and the Progress Report for product managers.
- Keep AI output advisory. Only the product manager approves tasks or requests changes.
- Let developers attach commits without copying links or hashes.
- Keep prompts small and focused (context engineering) and avoid repeat LLM calls (resource awareness).
- Keep project, task, GitHub, AI, and reporting responsibilities in separate modules.

**Non-Goals:**
- GitHub webhooks or real-time commit syncing.
- Running or testing submitted code. The AI only reads diffs.
- More than one repository per project.
- Email or chat notifications.

## Decisions

- **Keep integrations server-side.** GitHub and SoC LLM calls happen only in server code behind adapters (`src/server`). UI code never calls GitHub or the LLM. Provider output is untrusted and can never call task mutation services.

- **GitHub sign-in through Supabase Auth.** Supabase Auth with the GitHub provider gives a verified GitHub user ID and username, which the commit picker needs. Supabase Auth is used for identity and sessions only. Application tables are still accessed through the server-side repository layer and are not exposed through Supabase Data APIs.

- **Commit picker instead of pasted references.** Each project stores one linked repository and its GitHub App installation binding. The server lists that repository's available branches, lists commits with `author`, `since`, `until`, and `sha` (branch), and fetches diffs for selected commits with `GET /repos/{owner}/{repo}/commits/{sha}` or the compare endpoint for consecutive commits. It checks commit authorship against the developer's verified GitHub user ID before attaching anything.

- **GitHub App installation and repository linking.** The product manager can install or configure the environment's GitHub App for a GitHub account or organization. One installation can be reused for multiple projects and repositories; each project links exactly one repository. The approved flow starts a server-side setup attempt bound to the project and currently verified PM, carries single-use state through GitHub's installation redirect, verifies the installation through separate GitHub user authorization before listing repositories, creates a server-side repository-list snapshot, and allows the PM to select from that in-app list. Attempts and snapshots expire 10 minutes after creation. Attempt and snapshot data use normalized persistence; OAuth user tokens are never persisted. The installation ID from GitHub and all browser-supplied selection values remain untrusted until checked against the server-side attempt and verified repository snapshot. Final linking rechecks current App access, and failures leave an existing binding unchanged. GitHub may require an account owner or repository administrator to install the App or add a repository to an installation. Approved setup callback, snapshot-read, and final-link routes and payloads are specified in the GitHub Evidence spec.

- **Separate GitHub App and Supabase identities.** Supabase Auth remains responsible for application sign-in and session identity. The separate GitHub App OAuth user access token is used only during setup verification to verify the user's identity and installation/repository access before a repository list is produced. It is not used for commit, branch, or diff reads, and is not persisted or logged.

- **Repository-scoped installation tokens.** The server uses the environment's GitHub App ID and private key to mint a short-lived installation access token when it reads repository evidence. Each token is restricted to the one linked repository and read-only Contents and Metadata permissions. User and installation access tokens are never returned to clients, logged, or persisted. GitHub App access uses a replaceable adapter in `src/server`.

- **Acceptance Criteria Check without a score.** Output is a schema-validated list, with one entry per criterion (`addressed` | `not_addressed` | `unclear`, plus evidence quotes), and a list of possible gaps. The server verifies that each evidence quote appears in the assessed diff, and downgrades unverifiable criteria to `unclear`. A number would read as a grade of the developer and is hard to test, so there is none.

- **Context engineering for the check.** The prompt contains only the acceptance criteria and the filtered diff. Lockfiles, generated files, and binaries are dropped, and a fixed input budget applies. Files left out because of the budget are listed in the result.

- **Context engineering for the report.** Report input is structured activity (state changes, progress updates, submissions, check results, feedback, commit metadata), never diffs. Each item carries its task ID so the model can cite it, and the server checks every citation against the project's tasks. The range is at most 7 days, and the input has its own budget. A range whose activity exceeds the budget is refused, and the product manager is asked to choose a shorter range. Activity is never silently dropped.

- **Caching.** Check results are keyed by task, the sorted set of commit SHAs, a hash of the acceptance criteria, and a hash of the normalized repository path rules. Reports are keyed by project and date range, and are invalidated when activity is recorded in that range. An empty range is answered without an LLM call.

- **One LLM gateway.** All AI features call a single server module. It builds prompts with untrusted content separated from instructions, redacts secrets, enforces quotas, calls the SoC LLM adapter, validates output (one retry), and records usage. A fake adapter provides deterministic success and failure paths for tests.

- **Single timezone.** Dates and default ranges use SGT (UTC+08:00) for every project. Timestamps are stored in UTC.

- **Separate environments.** Development and production each have their own Supabase project, Vercel environment (`dev` branch preview and `master` production), GitHub sign-in OAuth app, GitHub App registration and credentials for repository linking/reads, SoC LLM credentials, and quota settings. Each GitHub App has its own installation per GitHub account or organization where it is used. The SoC LLM keys come from two different SoC accounts (see SoC LLM and Quota Decisions).

## SoC LLM Facts

The SoC LLM is SoCLaaS. These facts come from the SoC DocHub SoCLaaS guides (access, API, quickstart, usage-limits, and models pages, last modified between 29 August and 7 October 2026), saved and checked in the CS3227-2610-MP3 project on 16 October 2026. Facts marked *(MP3 key)* were observed with that project's API key and must be re-checked with this project's key.

- **API format.** An OpenAI-compatible gateway at `https://soclaas-api.comp.nus.edu.sg`. Endpoints are `GET /v1/models`, `POST /v1/chat/completions`, `POST /v1/responses` (a compatibility shim with non-durable state), `POST /v1/embeddings`, and `POST /v1/audio/transcriptions`. `POST /v1/chat/completions` is the primary endpoint and executes no tools in the gateway. `model` is required. Streaming uses server-sent events. The quickstart sends `"reasoning_effort": "none"` with Qwen and Gemma models.
- **Authentication.** `Authorization: Bearer <key>`. Keys have the form `clsk_<prefix>_<secret>`, are issued per SoC account through `https://soclaas-portal.comp.nus.edu.sg`, and rotating a key disables the old one at once. Keys must stay server-side.
- **Errors.** Bodies have the shape `{"error": "<message>"}`. 400 is an invalid request, 401 a missing, invalid, or revoked key, 403 a model or feature the key may not use, 429 a rate *or* budget limit, and 5xx a temporary gateway or backend fault. The guides recommend retry with backoff for 429 and 5xx and client-side timeouts. They do not document a `Retry-After` header.
- **Models.** Model names are operator-managed aliases, and `GET /v1/models` is the authoritative list for a key. A key that may not use a model does not see it there. The models page lists `llama3.1:8b` (65,536-token context), `qwen3.5:9b` (65,536), `gemma4:26b` (131,072), `qwen3-coder-next` (196,608), `qwen3.6:35b` (262,144), `qwen3.8:27b` (262,144), `qwen3-vl:32b` (80,000), and `ornith:35b` (262,144), plus trial models such as `x-test-1`. New or test models may appear before the page is updated. *(MP3 key)* On 16 October 2026 the list also had a `default` alias pointing to `qwen3.6:35b`, and operators can repoint it without notice.
- **Context window.** Per model, as above, reported by `GET /v1/models` in `context_length` (also `context_window`, `max_context_tokens`, and `max_model_len`).
- **Prices.** Prices are in microdollars per million tokens and are used only for rate control. No real money is charged. The authoritative source is `GET /v1/models` (`soclaas.input_microdollars_per_million_tokens` and `soclaas.output_microdollars_per_million_tokens`), because the models page was found to list outdated prices. *(MP3 key)* On 16 October 2026 `default` cost 411,810 per million input tokens and 1,456,571 per million output tokens.
- **Rate and budget limits.** Limits apply per API key. The current defaults are 90 requests per minute, 80,000,000 microdollars (USD 80) per day, and 800,000,000 microdollars (USD 800) per month. Lifetime credits and model access policy may also apply, and SoC may adjust any of these. The daily budget resets at 00:00 UTC (08:00 SGT), and the monthly budget at 00:00 UTC on the 1st. A key's actual limits can be read from `GET https://soclaas-portal.comp.nus.edu.sg/api-key/budget`. Requests over a limit are rejected with 429.
- **Token limits.** No tokens-per-minute or tokens-per-day limit is documented. Spending is limited by cost, which is computed from tokens and the model's prices.
- **Data retention.** The guides say only that SoCLaaS records API usage and request metadata against the key for reporting, quotas, and auditing. They say nothing about prompt or response retention, or about which data may be sent.
- **Reachability from Vercel.** A human-run smoke test in the CS3227-2610-MP3 project reached the endpoint and authenticated with an API key from a Vercel Hobby deployment on 11 October 2026. This project has not repeated the check.

## SoC LLM and Quota Decisions

Approved by thegrimbee on 26 October 2026. Cost estimates use the `qwen3.6:35b` prices observed on 16 October 2026: one check with a full input budget costs about USD 0.01, so the USD 80 daily key budget allows about 8,000 checks.

- **Model.** Both AI features use `qwen3.6:35b`, pinned by name rather than through the `default` alias, so cache keys and usage records name the model actually used. Before AI is enabled, `GET /v1/models` with this project's key must list the model, and its prices are read from there. If the name is retired, calls fail safe and the model is changed in configuration.
- **Keys per environment.** Development uses an API key from thegrimbee's SoC account, and production uses one from Lim-ZY's SoC account. Each environment therefore has its own full per-key limits, and replacing one key does not affect the other. The key owner uses the key only for this application, or warns the team before replacing it. Local development uses the fake adapter by default and the development key only when needed.
- **Limit split.** No split is needed while the environments use separate keys. If they ever share one key, production gets 60 requests per minute and USD 53.33 per day, and development 30 requests per minute and USD 26.67 per day.
- **Prompt retention.** Undocumented retention is accepted. Secret redaction and minimal prompts are the safeguards. Course staff may be asked in parallel, but this does not block work.
- **Vercel reachability.** No separate smoke test. After the first deployment with the real adapter, each environment makes one real call, and the result is recorded with the release checks.
- **Quota reset.** Per-person daily quotas reset at 00:00 SGT, matching the project's day boundary. SoCLaaS's 08:00 SGT reset does not affect them, because per-person quotas are far below the key budget.
- **Check input budget.** 16,000 tokens for the filtered diff, and 2,000 output tokens. Because no token-counting endpoint exists, input size is estimated at 3 characters per token, so the diff limit is 48,000 characters.
- **Report input budget.** 24,000 tokens, estimated the same way (72,000 characters), and 2,000 output tokens.
- **Maximum report range.** 7 days.
- **Per-person rate limit.** 5 AI requests per minute per person, in each environment. Requests answered from a cached result do not count.
- **Per-person daily token quota.** 400,000 tokens in production and 1,000,000 in development, where developers run the evaluation fixtures against the real model. Tokens are counted from the usage the provider reports. If a response has no usage, the request's maximum possible tokens are charged. The maximum is reserved before the call and settled afterwards, so concurrent requests cannot exceed the quota.

- **D10 Migrations.** CI does not apply migrations to any Supabase database, and GitHub holds no migration credentials. Migrations remain a controlled, operator-run release step. Applying the migrations to the disposable PostgreSQL service container used by the database integration tests (D9) is permitted, because that container is created and destroyed within the run.
- **D11 Vercel.** Vercel's Git integration deploys independently of GitHub Actions. Required checks on `master` (D7) keep unchecked code out of production. GitHub holds no Vercel secrets.

## Data Persistence Decisions

Approved by thegrimbee on 30 October 2026 for task 2.4. The human approved the `data-persistence` spec delta and asked the agent to resolve these decisions as it recommended. The numbering follows the task 2.4 analyst brief.

- **D-A Tooling and client.** Migrations are plain SQL files managed with the Supabase CLI, pinned as a development dependency and run by an operator (`supabase db push`) as the controlled release step. The application and the tests use `node-postgres` (`pg`) with parameterized queries and no ORM. Queries use unnamed statements only, so they work through the transaction pooler.
- **D-B Location.** Migrations live in `supabase/migrations/` as `<UTC timestamp>_<name>.sql`, the Supabase CLI format. Application tables live in a dedicated `app` schema, not `public`.
- **D-C Product-manager transfer.** Each project keeps exactly one product manager. Only the current product manager can transfer the role, and only to an existing developer in the project. In one transaction the outgoing product manager becomes a developer and the incoming developer becomes the product manager. The transfer is refused while the incoming developer has assigned tasks that are not Done; the product manager reassigns them first.
- **D-D Task IDs.** Every record keeps an opaque UUID as its identifier in the database and the API. Each project also has a key (2 to 10 uppercase letters and digits, starting with a letter, unique, fixed at creation). Each task gets a task ID `<project key>-<n>`, where `n` comes from a per-project counter incremented in the task-creation transaction and is never reused. Task IDs are what commit messages mention and what reports cite.
- **D-E Task deletion.** Deletion is soft: a deleted task keeps its row and history with a deletion timestamp. It disappears from the board and the review queue, is excluded from new reports, and its task ID is not reused. Recording the deletion invalidates stored reports for ranges that include it.
- **D-F Task events.** One append-only `task_events` table records state changes, submissions (with the check result attached at submission), assignment changes, and review feedback; feedback text is part of the request-changes event. Progress updates have their own table. "Changes requested more than once" is a count of request-changes events.
- **D-G Quota storage.** Usage records are created when a token reservation is made (outcome `pending`) and settled after the call, in a second transaction; no transaction is open during the LLM call. A per-person, per-SGT-day row is locked while reserving, so concurrent reservations are serialized. The daily quota is the sum of charged tokens, or reserved tokens for unsettled records, for that SGT day. The rate limit counts that person's non-cached records started in the last 60 seconds. A record left `pending` keeps its full reservation.
- **D-H GitHub App repository binding.** A project stores the GitHub App installation ID, stable GitHub repository ID, owner, and name for its one linked repository. The new identifier columns are `github_installation_id` and `github_repository_id`; both must be positive when set, and owner/name plus both identifiers are either all present or all absent. It stores no GitHub user or installation access token, App private key, or OAuth client secret. The existing task 2.4 schema's encrypted PAT columns are retired by a new versioned migration in task 5.1; the shipped migration is not edited. If legacy repository owner/name or encrypted PAT fields are populated, the migration clears those fields so the project is unlinked and can be relinked through the App. Developer A owns this migration as part of GitHub evidence task 5.1, by human decision on 3 November 2026.
- **D-H1 GitHub setup attempt and repository snapshot.** A normalized setup-attempt record binds project, current PM/person, expected verified GitHub user, candidate installation, single-use state, status, and creation/expiry timestamps. A normalized repository-list snapshot binds to that attempt, project, person, and installation and stores repository IDs and display/selection metadata; attempt and snapshot expire 10 minutes after their respective creation. No OAuth token is stored. A final repository selection rechecks current App access before changing the project binding.
- **D-H2 Section 5 migration ownership exception.** Developer A owns all Section 5 work, including the task 5.1 migration for GitHub binding, attempts, and repository snapshots. This is an explicit human-approved exception to the general AGENTS.md ownership statement that assigns database/migration work to Developer B. The shipped migration remains unchanged; PostgreSQL execution remains a required validation whose completion is not yet verified.
- **D-I People and Supabase Auth.** The `people` table has its own UUID, a unique `auth_user_id` (the Supabase Auth user ID, without a foreign key into the `auth` schema), a unique GitHub user ID, and the GitHub username, which is refreshed on each sign-in. Authorship checks use the GitHub user ID only.
- **D-J Roles and grants.** Migrations run as the Supabase `postgres` role by an operator. The application connects as `app_runtime`, which has only `SELECT`, `INSERT`, `UPDATE`, and `DELETE` on tables and `USAGE` on sequences in the `app` schema, and cannot create or alter objects. A migration creates `app_runtime` without a password; the operator sets its password outside the repository. `anon` and `authenticated` get no privileges on the `app` schema, and the schema is not added to the Data API's exposed schemas, so row-level security is not enabled. The Data API is turned off in the Supabase projects, which are in the Singapore region. Connections to Supabase use `sslmode=verify-full` and verify the server certificate against the Supabase root CA, which the app reads as PEM text from the server-only environment variable `DATABASE_CA_CERT`; certificate verification is never disabled. Operators pass the same CA to `psql` and `pg_dump` (`sslrootcert`).
- **D-K Test database.** Database integration tests run against a disposable PostgreSQL container, of the same major version as the Supabase projects (PostgreSQL 17; the projects report 17.11.0.011, recorded 30 October 2026), locally (Docker) and in CI (a service container). A test helper applies `supabase/migrations/*.sql` in order with `pg` and connects as `app_runtime` to test grants. The tests run as a separate Vitest project through `npm run test:integration`, so `npm test` needs no database. CI gains a `db-integration` job (D9), which becomes a required check.
- **D-L Backup and restore.** The first migration runs against empty databases, so its restore plan is to drop the `app` schema and the `app_runtime` role. Before every later migration, the operator takes a `pg_dump` of the `app` schema and stores it outside the repository. Restoring means loading that dump with `psql`. The developer guide documents both procedures.
- **D-M Column types.** Status and outcome values are `text` columns with `CHECK` constraints rather than PostgreSQL enums. A check result keeps its lookup fields as columns (task, sorted commit-set hash, criteria hash, normalized path-rules hash, model, redaction flag, created time) and the validated result (anchor SHA, per-criterion statuses, evidence, gaps, and skipped files) as `jsonb`. A report keeps project, range, model, the latest activity time it includes, and its validated statements with cited task UUIDs as `jsonb`; regenerating a report replaces the stored one. Usage outcomes are `pending`, `succeeded`, `invalid_output`, `provider_error`, and `cached`.
- **Task 2.4 review decisions.** Approved by thegrimbee on 30 October 2026, who asked the agent to resolve the task 2.4 reviewer's findings as it recommended.
  - *History is never hard-deleted (D-E, D-D).* `app_runtime` has no `DELETE` on `tasks`, so task numbers cannot be reused through a hard delete.
  - *Task events are append-only (D-F over D-J).* `app_runtime` has only `SELECT` and `INSERT` on `task_events`. Other tables keep the D-J privileges.

## Acceptance Criteria Check decisions

The following Group 7 behavior is approved:

- The 48,000-character budget is applied after redaction and file filtering. Files are included or omitted whole, and every eligible file omitted because of the budget is listed. Excluded lockfiles, generated files, and binaries are not listed as budget omissions. Each repository supplies deterministic, source-controlled path rules in root `.acceptance-check.json`. The version 1 JSON schema has exactly `version`, `domainLogic`, `apiHandlers`, `tests`, `ui`, `lockfileNames`, and `generatedPathPrefixes`: `version` is the integer `1`; the four categories and `generatedPathPrefixes` are required arrays of literal repository-relative directory prefixes using `/` and ending in `/`; and `lockfileNames` is a required array of exact, case-sensitive literal basenames. No extra properties are allowed. Lockfile exclusion matches exact basenames; generated-file exclusion uses literal, boundary-aware prefix matching; binary exclusion uses GitHub's binary-diff marker. For renames, the destination path is used for exclusion and classification, and the rename is one file entry. Exclusions apply before classification and budgeting. Duplicate values are removed and each array is sorted lexicographically to form normalized rules. The normalized hash uses compact UTF-8 JSON with fixed property order `version`, `domainLogic`, `apiHandlers`, `tests`, `ui`, `lockfileNames`, `generatedPathPrefixes`. A path matching more than one category belongs to the first matching category in this fixed priority: domain logic, API handlers, tests, UI. Prefix matching is boundary-aware and literal, without glob or regular-expression interpretation. An unmatched eligible file belongs to `other`.
- Path rules are read independently of the selected commit set: for each check request, resolve the linked repository's current default-branch tip and fetch `.acceptance-check.json` at that immutable commit SHA. This lets a repository policy change produce a new assessment of the same commits. Missing, invalid, or unavailable configuration fails safely with `EVIDENCE_UNAVAILABLE` before an LLM call or check-result write. The normalized path-rules hash is SHA-256 over compact UTF-8 JSON with properties in the fixed order above and the normalized arrays; a change in array ordering or duplicate entries alone does not change the hash.
- Process files by priority group and alphabetically within each group. Include each whole file that fits; if a file does not fit, omit it and continue considering later files. Report every eligible file omitted due to the budget. This is consistent with Secret Redaction Decision D4 above.
- Cache reuse requires the same task, commit-set hash, criteria hash, and normalized path-rules hash. A changed normalized rules hash permits a distinct result for the same commits and criteria. A new versioned migration adds nullable `check_results.path_rules_hash`, constrains non-null values to lowercase 64-character SHA-256 hex, drops the existing two-key reuse constraint, and adds a partial unique key on `(task_id, commit_set_hash, criteria_hash)` where the path-rules hash is null plus a partial unique key on `(task_id, commit_set_hash, criteria_hash, path_rules_hash)` where it is non-null. Existing rows remain unchanged with a null path-rules hash, stay visible as history, and are not cache hits for new requests. New check writes always supply the validated hash. Developer B owns this database migration and its persistence tests under the repository ownership rules; Developer A owns the Acceptance Criteria Check service. The shipped migration is not modified.
- **Group 7 hash and result contracts.** The commit-set hash is SHA-256 over the full commit SHAs sorted lexicographically and joined by LF, with no trailing LF. The criteria hash is SHA-256 over compact UTF-8 JSON for `{ "id", "description" }` criterion objects, ordered by position then criterion ID and serialized with `id` before `description`. Task ID is a separate key dimension. The model receives each current criterion's stable ID and text. The validated result JSON has exactly `anchorSha`, `criteria`, `possibleGaps`, and `omittedFiles`; each criterion result has exactly `criterionId`, `criterion`, `status`, and `evidence`, with statuses `addressed`, `not_addressed`, or `unclear`, and evidence as exact diff-line strings. No database transaction remains open during GitHub or LLM network calls. ### Check route contract

The assigned developer calls `POST /api/v1/projects/{projectId}/tasks/{taskId}/acceptance-criteria-check` with exactly `{}` as the JSON request body. The server derives attached commits and criteria from the task. Success returns HTTP 200 `{ "check": <check result>, "reused": <boolean> }` with `Cache-Control: no-store`. A check result exposes its result ID, anchor SHA, creation timestamp, redaction flag, and result payload. A cache hit returns the existing check with `reused: true`; a newly created result returns `reused: false`.

- Malformed JSON, a body other than exactly `{}`, or malformed UUIDs return the existing HTTP 400 `INVALID_REQUEST`. Unauthenticated requests return HTTP 401 `UNAUTHENTICATED`; PM initiation returns HTTP 403 `FORBIDDEN`; a missing task or non-member returns HTTP 404 `NOT_FOUND`. No attached commits returns HTTP 409 `CHECK_REQUIRES_COMMITS`; a selected set without a unique descendant tip returns HTTP 409 `INCOMPARABLE_COMMIT_TIPS`. Rate and quota refusals use HTTP 429 `RATE_LIMITED` and `QUOTA_EXCEEDED`; provider unavailability uses HTTP 503 `AI_UNAVAILABLE`; other AI failures and invalid model output use HTTP 502 `AI_ERROR` and `INVALID_OUTPUT`; unexpected internal failures use HTTP 500 `INTERNAL_ERROR`. Errors use the existing safe JSON envelope `{ "error": { "code": "...", "message": "..." } }` and do not expose provider details.

The task-scoped route, empty-object request, HTTP 200 response envelope, history entry fields, submission matching rule, domain errors, and AI error mapping above are approved contract decisions. Existing task-detail and review response bodies expose `checkHistory` using that entry shape. Missing, invalid, or unavailable repository path configuration uses the existing HTTP 503 `EVIDENCE_UNAVAILABLE` response; unexpected service or database failures use HTTP 500 `INTERNAL_ERROR`.

## LLM Adapter Decisions

Approved by thegrimbee on 1 November 2026 for task 6.1. The human approved the `ai-safeguards` requirement "The LLM provider is behind a replaceable adapter" and asked the agent to resolve these decisions as it recommended. The numbering follows the task 6.1 analyst brief.

- **D1 Spec home.** Adapter behaviour is a requirement of the `ai-safeguards` capability, not a separate capability.
- **D2 Adapter contract.** The application defines one interface in `src/server/ai/` with one method, `complete`. Its request holds an ordered list of messages (role `system` or `user`, plain-text content) and a maximum number of output tokens. The gateway builds the messages; the adapter sends them unchanged. The SoC adapter calls `POST /v1/chat/completions` with the configured model, the messages, `max_tokens`, `"reasoning_effort": "none"` (a provider detail kept inside the adapter), and no streaming. It does not request a JSON response format, which the SoC guides do not document; the gateway validates output against the feature schema. `complete` resolves to either a success or a failure and does not reject for provider failures. A success holds the text of the first choice, the model name from the provider response (or the requested model if the response has none), and usage as input and output tokens, or no usage when the provider omits it or reports values that are not non-negative integers. A failure holds only a category and, where one exists, the HTTP status: `invalid_request` (400), `unauthorized` (401), `forbidden` (403), `rate_limited` (429), `unavailable` (5xx or a network failure), `timeout`, and `malformed_response` (any other status, a body that is not JSON, or no text). No provider message, response body, or credential appears in a failure. Callers see only these application types.
- **D3 Configuration and wiring.** The adapters take their settings (key, model, and an injectable `fetch` for tests) as constructor arguments and read no environment variable, so task 6.1 does not create `src/server/config/` or `src/server/composition.ts`. Task 6.3, which first runs the gateway, selects the adapter from `AI_PROVIDER` in the composition root, unless task 3.1 or 5.1 has created the configuration module first. This amends E5's list of tasks that may create the module to 3.1, 5.1, or 6.3. The spec scenario "Adapter selected by configuration" is verified by the task that wires the composition root.
- **D4 Timeout and retry.** Each SoC call is one attempt with a 60-second timeout, a code constant. Neither the adapter nor the gateway retries 429, 5xx, network failures, or timeouts; the user sees a safe error and may try again. The gateway's single retry is only for schema-invalid output, so a request makes at most two calls. Task 6.3 confirms that the Route Handler's maximum duration on Vercel covers two calls. The adapter uses the built-in `fetch` with an abort signal; no SDK or other dependency is added.
- **D5 Rate versus budget limits.** Both are reported as `rate_limited`, because 429 does not say which limit was hit.
- **D6 Fake adapter.** The fake adapter takes an optional ordered script of outcomes. Each call returns the next outcome: a success with given text and given usage (or no usage), or a failure with a given category. Once the script is used up, or when none is given, each call returns a fixed success whose text is a constant and whose usage is estimated at 3 characters per token from the request and the text. The fake reports the model name `fake`, so its results are never mistaken for real-model results in caches or usage records. Feature-specific canned output that passes a feature schema is added by the tasks that add those features.
- **D7 Logging.** The adapters do not log. They return metadata to the gateway, which records usage without prompt or response content.
- **D8 Model availability.** Checking that `GET /v1/models` lists the pinned model stays a manual step before AI is enabled (developer guide) and in the release checks. The adapter has no model-listing method.

## Secret Redaction Decisions

Approved by thegrimbee on 2 November 2026 for task 6.2. The human approved the new `ai-safeguards` requirement "Redaction is complete, marked, and reported", which extends "Secrets are redacted before LLM calls" (split in two to meet the OpenSpec requirement length limit), and approved these decisions as the analyst recommended. The numbering follows the task 6.2 analyst brief.

- **D1 Pattern coverage.** Redaction covers known token formats and keyword assignments. It uses no entropy heuristics, which would corrupt hashes, UUIDs, and lockfiles in diffs. The patterns are: GitHub tokens (`ghp_`, `gho_`, `ghu_`, `ghs_`, `ghr_`, `github_pat_`); SoC LLM keys (`clsk_<prefix>_<secret>`); AWS access key IDs (`AKIA` or `ASIA` followed by 16 characters); PEM private key blocks from `-----BEGIN ... PRIVATE KEY-----` to the matching `END` line, including a truncated block with no `END`; JWTs (three base64url segments, the first starting `eyJ`); Supabase secret keys (`sb_secret_`; `service_role` JWTs are covered by the JWT pattern); `postgres://`, `postgresql://`, `mysql://`, `mongodb://`, `mongodb+srv://`, `redis://`, and `rediss://` (TLS Redis, added by human decision during task 6.2) URLs with `user:password@` credentials; `Authorization: Bearer <value>`; and assignments with `=` or `:` whose key name contains `password`, `passwd`, `secret`, `token`, `api_key` or `api-key` or `apikey`, `private_key` or `private-key`, or `access_key` or `access-key`, where the value is redacted and the key name kept. A key name matches only as a whole word or a whole `_`, `-` or `.` segment, case-insensitively, so `max_tokens` does not match. The value must be a literal: a quoted string, or a bare value with no spaces, parentheses, or type syntax. So `password: string` and `const token = getToken()` are not redacted (human decision during task 6.2, 2 November 2026). In a connection URL only the password is replaced, for example `postgres://user:[REDACTED:connection-string]@host/db`. For `Authorization: Bearer <value>`, matched case-insensitively, the `Authorization: Bearer ` prefix is kept and the value is replaced with `[REDACTED:bearer-token]`, even when the value is a JWT or another token.
- **D2 Marker.** Each secret is replaced by a typed marker `[REDACTED:<kind>]`, for example `[REDACTED:github-token]`. A keyword assignment keeps its key name, for example `password=[REDACTED:credential]`. The marker never contains a hash or any part of the secret. The kinds are `github-token`, `soc-llm-key`, `aws-access-key`, `private-key`, `jwt`, `supabase-secret-key`, `connection-string`, `bearer-token`, and `credential` (human decision during task 6.2, 2 November 2026).
- **D3 Result and visibility.** Redaction returns the redacted text, the number of replacements, and the kinds found, never the matched text. The gateway and feature services decide what to store. The Acceptance Criteria Check stores its existing redaction flag in `check_results` (Data Persistence Decisions). Progress Reports store nothing new. The check UI shows a concise note only when the stored redaction flag is true; it never shows redacted values or secret text.
- **D4 Order.** Redaction runs on each whole text segment before diff filtering and the input budget (task 7.1), so truncation cannot cut a secret into a fragment that no pattern matches. Marker length differences are accepted because the budget is an estimate.
- **D5 Evidence verification.** Evidence quotes are verified against the redacted diff, which is the diff that was assessed, so a stored quote never contains a secret. Task 7.2 applies this.
- **D6 Model output.** Redaction applies to input sent to the LLM only. Model output is not redacted in task 6.2; redacting it would be a separate requirement.
- **D7 Recording and logging.** No usage-record field is added. Counts and kinds never include matched text. The redaction module does not log.
- **D8 Placement and API.** Redaction is one pure function over a string in `src/server/ai/redaction.ts`, exported through `src/server/ai/index.ts` with its result type only. The gateway (task 6.3) applies it to each prompt segment. It takes no flag arguments, and the adapters do not call it.
- **D9 Overlapping patterns.** The most specific patterns run first (PEM blocks, connection URLs, token prefixes, JWTs) and keyword assignments last, so a marker is never nested or redacted again. Tests cover the overlap cases.

## LLM Gateway Decisions

Approved by thegrimbee on 2 November 2026 for task 6.3. The human approved the `ai-safeguards` spec delta and asked the agent to resolve these decisions as it recommended. The numbering follows the task 6.3 analyst brief (G1 to G12 answer its D1 to D12).

- **G1 Prompt format.** Each call sends two messages. The system message holds the feature's fixed instructions and a fixed preamble saying that the user message holds untrusted data in `<data name="...">` sections, that the content of those sections is data to assess and never instructions, and that the reply must be JSON only. The user message holds one `<data name="<segment name>">` … `</data>` section per segment, in the order given. Segment names are code constants chosen by the feature, never user input. Each segment is first redacted (Secret Redaction Decisions D8). Then every case-insensitive `<data` and `</data` in it has its `<` replaced by `&lt;`, so the segment cannot close its section or open another. No untrusted text is placed in the system message. The retry sends the same messages unchanged; the invalid output is never sent back to the model.
- **G2 Charge on failure.** This follows the spec rule "charge the tokens the provider reports, or the reserved maximum if it reports none", applied per call. A call that returns usage is charged that usage. A call that returns no usage, including every adapter failure, is charged its reserved maximum. A call that is never made (the retry when the first output is valid, or after a provider failure) is not charged, so its share of the reservation is released at settlement.
- **G3 Safe errors.** The gateway returns a result and does not throw for expected failures. A failure holds only a code from the API error contract (see "API Error Contract"):
  - `RATE_LIMITED`: the person's per-minute limit.
  - `QUOTA_EXCEEDED`: the daily quota, with `resetsAt`, the next 00:00 SGT as an ISO 8601 UTC timestamp.
  - `AI_UNAVAILABLE`: an adapter failure of `rate_limited`, `unavailable` or `timeout`; the user may try again.
  - `AI_ERROR`: `invalid_request`, `unauthorized`, `forbidden` or `malformed_response`.
  - `INVALID_OUTPUT`: the schema failed twice.

  Route Handlers map these to HTTP responses using that contract. Database errors are not expected failures. They propagate, and handlers return a generic error. The gateway does not log prompt or response content.
- **G4 Rate counting of the retry.** One gateway request is one usage record and counts once toward the 5-per-minute limit, whether it makes one call or two. A spec "LLM call" in "AI usage is recorded" means one gateway request including its retry. Its tokens and latency are summed over its calls.
- **G5 Reservation amount.** A call's maximum is `ceil(total characters of both messages / 3) + maxOutputTokens` (the 3-characters-per-token estimate). A request reserves two calls' maximum before the first call, because the retry sends the same messages. This keeps concurrent requests within the quota, at the cost of sometimes refusing a request near the limit that would have needed only one call. A request is allowed when the day's charged and reserved tokens plus this reservation do not exceed the daily quota.
- **G6 Rate window.** The reservation transaction locks the person's `usage_quota_days` row for the current SGT date, `(now() AT TIME ZONE 'Asia/Singapore')::date`. It then checks the rate limit and the quota, and inserts the `pending` record, all with database time. The rate limit counts the person's records with `cached = false` and `created_at > now() - interval '60 seconds'` in any outcome, so a record exactly 60 seconds old no longer counts. The daily total covers records whose `created_at` falls on that SGT date. Refused requests leave no record; the outcome list is unchanged.
- **G7 Cache split.** The gateway owns no cache. Feature services (tasks 7.2 and 8.2) look up their own caches. On a hit they call the gateway's cache-hit recorder, which inserts one record with outcome `cached`, `cached = true`, and zero reserved and charged tokens, with no rate or quota check.
- **G8 Ownership and seam.** Task 6.3 is done by thegrimbee (Developer B, owner of database, migrations and usage logging), and Lim-ZY cross-reviews. The gateway in `src/server/ai/` depends on a usage port (an interface it defines) with three operations: reserve, settle and record cache hit. The PostgreSQL implementation lives in `src/server/repositories/usage-repository.ts`; it is the only writer of `usage_records` and `usage_quota_days`. Task 6.3 adds the new migration with the `usage_records.environment` `CHECK` (Environment Decisions E6) and PostgreSQL integration tests for concurrent reservations, the SGT day boundary and the constraint. The AI security evaluation fixtures stay with Developer A and are not part of task 6.3.
- **G9 Gateway API.** One method, run, takes:
  - the feature (`acceptance_check` or `progress_report`);
  - the project UUID and person UUID;
  - the feature's fixed instructions;
  - the ordered named segments;
  - `maxOutputTokens`;
  - a validator.

  The validator is a hand-written function from the parsed JSON value to the typed result or a rejection; no validation library is added (E5). The gateway trims the response and removes one surrounding Markdown code fence if present. It then parses JSON; output that does not parse counts as schema-invalid. A success holds the validated value, the model name, and the redaction summary (count and kinds summed over segments) so feature services can store their redaction flag (Secret Redaction Decisions D3). The limits table from E4 is a constant in `src/server/ai/` keyed by `APP_ENV`. The gateway is built in the composition root with the selected adapter, the usage repository, and the environment's limits.
- **G10 AI configuration.** `getServerConfig` also reads `AI_PROVIDER`, which is required everywhere and must be `fake` or `soclaas`. When it is `soclaas`, `SOCLAAS_API_KEY` must be non-empty and `SOCLAAS_MODEL` must be non-empty and not `default`. When it is `fake`, those two are not read. `APP_ENV=production` with `AI_PROVIDER=fake` fails. Errors name the variable, never the value. The existing test that every variable read is listed in `.env.example` covers the new variables.
- **G11 Route duration.** No Route Handler exists in task 6.3. The first AI Route Handler (task 7.3 or 8.2) sets `maxDuration` to at least 150 seconds (two 60-second calls plus database work). The release checks confirm the Vercel plan allows it.
- **G12 Usage view.** The per-feature, per-day usage queries and the product manager's usage view are not part of task 6.3. They belong to the task that builds that view.
- **Task 6.3 handoff decisions.** Approved by thegrimbee on 2 November 2026, answering the orchestrator's questions Q1–Q6 in `workflow/handoffs/llm-gateway-core.md`.
  - *Q1 Charged tokens.* The 6.3 migration also adds a nullable `usage_records.charged_tokens` integer column (non-negative), set at settlement and for cache hits (0). It amends D-G's quota sum: the daily total is `charged_tokens` for settled records plus `reserved_tokens` for `pending` records. `input_tokens` and `output_tokens` hold only provider-reported usage, summed over the calls that reported it.

## API Error Contract

Recorded on 2 November 2026 during task 6.3. `AGENTS.md` refers to an API error contract in `openspec/`, but none had been recorded. thegrimbee chose to record the format that the existing auth Route Handlers (`src/app/api/v1/auth/`) already use. Approved by Lim-ZY (Developer A, API owner) on 2 November 2026.

- **Shape.** Every `/api/v1` error response is JSON of the form `{ "error": { "code": "<CODE>", "message": "<safe text>" } }`. Fields specific to a code go in `error` next to `code` and `message`, for example `resetsAt` for `QUOTA_EXCEEDED`.
- **Codes.** Codes are stable `UPPER_SNAKE_CASE` strings that clients may depend on. A code is added by the task that first returns it, and recorded here. Existing codes:
  - `AUTHENTICATION_FAILED` (500 or 502).
  - `EVIDENCE_UNAVAILABLE` (503): repository evidence, including the current default-branch path-rules file, cannot be retrieved or validated.
  - `FORBIDDEN` (403).
  - Shared by the existing Route Handlers and recorded during task 4.1: `INVALID_REQUEST` (400), `UNAUTHENTICATED` (401) and `NOT_FOUND` (404).
  - The LLM Gateway Decisions G3 codes: `RATE_LIMITED` (429), `QUOTA_EXCEEDED` (429), `AI_UNAVAILABLE` (503), `AI_ERROR` (502) and `INVALID_OUTPUT` (502).
  - `PROJECT_KEY_TAKEN` (409): a project key already exists (task 4.1).
  - `TRANSFER_BLOCKED_OPEN_TASKS` (409): the incoming product manager has open assigned tasks (task 4.1).
  - `GITHUB_USERNAME_AMBIGUOUS` (409): a GitHub username matches more than one registered person (task 4.1).
  - `ALREADY_MEMBER` (409): the person already has a role in the project (task 4.1).
  - `TRANSFER_TARGET_NOT_DEVELOPER` (409): the transfer target is not a developer in the project, or is the product manager (task 4.1).
  - `ACCEPTANCE_CRITERIA_REQUIRED` (400): a task has no acceptance criteria (task 4.2, T7).
  - `ASSIGNEE_NOT_DEVELOPER` (409): a task assignee is not a developer in the project (task 4.2, T7).
  - `VERSION_CONFLICT` (409): a task write used a version that is no longer current (task 4.2, T6, T7; also the task state route, task 4.3, L1). Task 4.3 adds no new code (L2).
- **Message.** A fixed, human-readable message chosen by the server. It never contains a stack trace, SQL, a provider message or body, a credential, or user-supplied text.
- **Headers.** Error responses send `Cache-Control: no-store`.
- **Unexpected errors.** Errors not mapped to a specific code return 500 with a generic message, and their details are not exposed.

## Risks / Trade-offs

- **The GitHub App can read the whole linked repository.** Each installation access token is short-lived and restricted to the one linked repository with read-only Contents and Metadata permissions. Tokens are never returned to clients, logged, or persisted, and the App private key stays in server-side environment variables (see "Repository-scoped installation tokens"). This bullet replaces an earlier one that described an encrypted personal access token, which the GitHub App change retired (corrected 6 November 2026 during task 4.1).
- **Developers commit with an email that is not linked to their GitHub account.** Those commits won't match the author filter. The commit picker explains this when no commits are found.
- **The model may judge criteria wrongly.** Results are advisory, evidence is verified against the diff, and only the product manager can approve.
- **Prompt injection through commits or task text.** This is mitigated by separating untrusted content, validating against the schema and evidence rules, and giving AI no ability to change state. Adversarial fixtures check it.
- **The school's LLM limits may be low.** The defaults are 90 requests per minute and USD 80 per day per API key, and 429 does not say whether the rate or the budget limit was hit. This is mitigated by caching, input budgets, per-person quotas, and usage records.
- **The model alias can change.** Operators can repoint a model alias or change its prices without notice. Results and usage records should store the model name used.
- **SoCLaaS does not document prompt retention.** Prompts carry task text and diffs, so secret redaction and small, task-focused prompts matter even more.
- **Large diffs exceed the input budget.** The check assesses what fits and lists the files it skipped, instead of silently truncating.
